# Target Inventory

Как составить перечень страниц, элементов и чек-кейсов для целевого проекта. Навык не содержит готового каталога страниц: inventory всегда выводится из исходников конкретного проекта и обновляется при дрейфе.

## 1. Перечень страниц/маршрутов

Выводить из исходников проекта, в порядке приоритета:

1. Роутер/карта маршрутов (файлы маршрутизации, страницы-компоненты, манифест навигации).
2. Компоненты навигации (меню, хедер, футер) — какие пункты реально видны пользователю.
3. Sitemap/manifest, если проект его ведёт.
4. Тестовые фикстуры/существующие UI-тесты проекта — какие маршруты уже считаются значимыми.

Для каждого маршрута зафиксировать: URL, требует ли аутентификации, какой странице принадлежит.

## 2. Ключевые элементы и стабильные селекторы

- Искать существующие стабильные идентификаторы (`data-testid`, aria-label, устоявшиеся id) в шаблонах/компонентах проекта.
- Не изобретать селекторы для сгенерированных классов: авторитет — живой `browser_snapshot` и его `ref`.
- Формы: перечень полей с labels, сообщения валидации, submit.

## 3. Чек-кейсы

Формулируются из приёмочных критериев видимого поведения (спецификация релиза или запрос пользователя), а не из каталога навыка:

| Проверка | Шаги | Ожидаемый видимый результат |
| --- | --- | --- |
| <сценарий> | <шаги из interaction-patterns.md> | <что видно на странице> |

Покрывать happy path каждой функции из области проверки плюс самый ценный путь отказа (auth gate, пустое состояние, ошибка валидации).

## 4. Viewport-брейкпоинты

Брать из дизайн-системы целевого проекта (CSS-переменные, media queries, токены). Если проект их не объявляет — использовать распространённый минимум: мобильный ~375, планшет ~768, десктоп ~1280, и зафиксировать, что брейкпоинты выведены по умолчанию, а не из проекта.

## 5. Правило дрейфа

Inventory — стартовая точка. Живой `browser_snapshot` всегда авторитетнее записанного перечня: расхождение между inventory и фактической страницей — наблюдение для отчёта, а не основание «подогнать» assertion.
