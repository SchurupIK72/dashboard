# Playwright Testing

**Ad-hoc навык** — UI/визуальная проверка через browser-инструменты, реально доступные в сессии основного агента; совместимый Playwright MCP также поддерживается.

Запускается ad-hoc — по триггеру, в любой момент: визуальная/интерактивная проверка без привязки к релизу. В маршрут workflow не встроен.

`write-tests` (шаг ③) владеет кодовыми тестами; этот навык — браузерными/UI-проверками видимого поведения. Docs-only релизы UI-прогона не требуют: применимость объясняется словами, без фиктивного прогона.

## Workflow Contract

```yaml
entry:
  mode:
    ad-hoc:
      condition: явный запрос на визуальную/UI-проверку
  prerequisites:
    - identity окружения доказана (см. «Проверка identity окружения»)
    - в сессии доступны browser-инструменты (перечислены фактически)

exit:
  condition: >
    проверки выполнены, либо явно вынесен вердикт blocked с причиной;
    скриншоты и логи зафиксированы в файлах
  artifacts:
    - каталог артефактов запуска: screenshots, console/network логи

next_skill: N/A (ad-hoc; возврат в контекст вызова)
```

## Проверка identity окружения (до любого шага браузера)

Перед любой UI-проверкой или замером доказать, что процесс/стенд принадлежит проверяемому repo/worktree и ревизии:

1. Зафиксировать ожидание: путь worktree, из которого идёт проверка, его ревизию (`git rev-parse HEAD`) и base URL.
2. Доказать принадлежность хотя бы одним способом:
   - процесс на порту запущен этим запуском, PID и команда записаны;
   - командная строка/рабочий каталог процесса указывают на этот worktree;
   - стенд отдаёт маркер ревизии/сборки (meta-тег, endpoint версии, строка старта в логе), совпадающий с ревизией worktree.
3. HTTP 200 или занятый порт — НЕ доказательство identity: на порту может отвечать соседний клон или чужой процесс. Такой endpoint не принимается как подтверждение.
4. Тестовые данные изолированы: только выделенные тестовые аккаунты/фикстуры, объявленные в предусловиях; реальные пользовательские аккаунты и общие базы запрещены. Fixture-предусловия проверены до начала.
5. Identity не доказана, стенд чужой или данные заняты чужим процессом → вердикт **blocked** с причиной и наблюдением, что фактически найдено. Не имитировать проверку и не «лечить» красный прогон остановкой чужих ресурсов.

## Cleanup с подтверждённым ownership

- Останавливать только процессы, запущенные этим запуском: по записанным PID, перепроверив командную строку перед остановкой.
- Удалять только данные, созданные этим запуском, и только в проверенной тестовой среде.
- Чужие процессы, dev/prod базы не останавливаются и не очищаются ради зелёных проверок.

## Гибридный метод

Каждую страницу проверять по цепочке (детали — в references):

1. **`browser_snapshot`** — accessibility-дерево + `ref` каждого элемента; главное средство навигации и взаимодействия.
2. **`browser_take_screenshot`** — визуал: композиция, общее впечатление.
3. **`browser_console_messages`** — JS-ошибки и нарушения политики безопасности контента; результат — в файл.
4. **`browser_network_requests`** — упавшие API-вызовы, 404-ассеты; результат — в файл.
5. **Адаптив** — инструментом смены viewport, если он есть в сессии; иначе зафиксировать как ограничение.
6. **Визуальная рубрика** (`references/visual-review.md`) — токены проекта, контраст WCAG, раскладка, состояния.

Каждый шаг сценария: **действие → ожидание → наблюдение → assertion**.

## Доступные инструменты — никаких выдуманных API

- Опираться на базовый набор: `browser_navigate`, `browser_click`, `browser_type`, `browser_select_option`, `browser_press_key`, `browser_wait_for`, `browser_take_screenshot`, `browser_snapshot`, `browser_console_messages`, `browser_network_requests`.
- Сначала перечислить browser-инструменты, реально доступные в сессии; вызывать только существующие.
- Параметры сужения области snapshot (глубина дерева, поддерево элемента) использовать только если инструмент сессии их действительно поддержит; неподдерживаемые параметры называть неподдерживаемыми, не предполагать.
- Инструменты вне базового набора (чтение вычисляемых стилей, hover, заполнение форм одним вызовом) — только при фактическом наличии; их отсутствие — ограничение или blocked, не фиктивный PASS.

## Правила

1. **Кликать по `ref` из snapshot**, не конструировать селекторы с нуля: `browser_snapshot` → `target: ref="..."`.
2. **Точные значения (цвета, отступы, размеры) — из DOM/CSS** доступным инструментом вычисляемых стилей; если такого нет — зафиксировать ограничение, не угадывать по скриншоту.
3. **Всегда консоль после навигации**; нарушение политики безопасности контента в консоли = баг, не косметика.
4. **Артефакты в файлах** каталога запуска: скриншоты и логи не раздувают контекст; cleanup своих артефактов после успешной проверки (оставлять только при fail/баг-репорте).
5. **Явные waits** (`browser_wait_for`) перед взаимодействием, не тайминги.
6. **Минимальная область snapshot**: снимать то, что нужно шагу; сужение — только реально поддерживаемыми параметрами.
7. **Свежий контекст** браузера для auth-сценариев.
8. **Недоступная browser-capability → blocked** с причиной; фиктивный UI PASS запрещён.

## Алгоритм

### Фаза 1: ENTRY

1. Подтвердить ad-hoc-запрос на визуальную/UI-проверку.
2. Перечислить доступные browser-инструменты сессии; отсутствуют → blocked с причиной.
3. Доказать identity окружения (см. выше); недоказуема → blocked с причиной и наблюдением.
4. Стенд не поднимается → запустить командой из предусловий сценария/подсказок окружения; readiness — `scripts/smoke-test.*` (доступность, не identity) или `browser_navigate`.

### Фаза 2: Разведка страницы

1. `browser_navigate` → URL.
2. `browser_snapshot` (минимальная необходимая область).
3. `browser_take_screenshot` (full-page для контекста).
4. `browser_console_messages` + `browser_network_requests` — в файлы.

### Фаза 3: Взаимодействие

Сценарии (`references/interaction-patterns.md`): form / modal / tab / auth. Каждый шаг: действие → wait → snapshot/screenshot → assertion. Дефект фиксируется с доказательством (шаг/ожидание/факт + файл), прогон продолжается до конца.

### Фаза 4: Адаптив + визуальная оценка

1. Адаптив доступным viewport-инструментом по брейкпоинтам целевого проекта (`references/target-inventory.md`); snapshot+screenshot на каждом размере.
2. Рубрика `references/visual-review.md`.

### Фаза 5: Отчёт + cleanup

- Pass/fail по каждому чек-кейсу; для fail — воспроизводимые шаги.
- Артефакты в файлах; cleanup после успеха.
- Cleanup — только своих подтверждённых процессов/данных.

## Continuous Improvement

По завершении каждого запуска выполни Improvement Triage:

1. Задача решена без неоднозначностей → вывести `no_change`.
2. Обнаружен повторно применимый урок → добавить краткую запись в `LEARNINGS.md`.
3. Инструкция навыка привела к ошибке → сначала создать eval-кейс в `EVALS.md`.
4. Предлагать патч `SKILL.md` только если та же проблема может повториться.
5. Предпочитать замену или удаление устаревшего guidance добавлению новых правил.
