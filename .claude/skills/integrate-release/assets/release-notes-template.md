# Release Notes Templates

Файлы `.ai/release-notes/{version}.md` — пользовательское описание изменений, которое доставляется пользователям при обновлении версии. Аудитория — пользователи продукта, не разработчики.

## Spec Route

```markdown
# v{version} — {date}

{2–3 предложения summary на русском — что нового в релизе. Без терминов «рефакторинг», «модуль», «репозиторий». С фокусом на пользу для пользователя.}

🆕 Что нового
• {пункт} — {пояснение для пользователя, почему это полезно}
• {пункт} — {пояснение}

🔧 Что исправлено
• {что было не так} — {что теперь работает}
• {что было не так} — {что теперь работает}

⚠️ Заметки
• {что нужно знать пользователю — изменения поведения, требующие действий с его стороны}

📌 Ограничения
• {известные ограничения — опционально, удалить секцию если нет}
```

## Small-Fix Route

```markdown
# v{version} — {date}

{1–2 предложения summary на русском — что исправлено.}

🔧 Что исправлено
• {что было не так} — {что теперь работает}
```

## Правила

- Заголовок файла — `# v{version} — {date}` с `v` префиксом. Доставщик сообщения (бот уведомлений, рассылка) отбрасывает эту строку перед отправкой.
- Emoji-секции со стандартными маркерами: `🆕 Что нового`, `🔧 Что исправлено`, `⚠️ Заметки`, `📌 Ограничения`. Это позволяет пользователю быстро сканировать сообщение.
- Каждый пункт — с буллетом `•` (не `-`), в одну-две строки, с пояснением после тире.
- Удалять секции без содержания, а не оставлять пустые заголовки.
- Стиль — конкретика для пользователя: «видите timeline этапов», «обновите привязки», а не «реализован cascade P1/P2».
- Запрещены: пути модулей, имена файлов, `**Компоненты:**`, `**Tests:**`, идентификаторы требований (FR-1, Р-7), имена фреймворков.
- Длина — комфортная для чтения без прокрутки: до ~30 строк.
