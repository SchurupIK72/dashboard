# Release Notes Entry

`.ai/release-notes/{version}.md` — обязательный release artifact integrate-release. Пользовательское описание изменений релиза. Аудитория — пользователи продукта, не разработчики.

## Отличия от CHANGELOG

| Слой | CHANGELOG | release notes |
|---|---|---|
| Аудитория | разработчики | пользователи |
| Стиль | технический | разговорный русский |
| Секции | `### Added/Fixed/Changed` + `**Компоненты:**` + `**Tests:**` | `🆕/🔧/⚠️/📌` |
| Длина | без лимита | до ~30 строк (компактный формат) |
| Контент | модули, paths, tests passed | польза для пользователя, действия с его стороны |

Оба артефакта создаются на один релиз и должны быть согласованы по фактам (что добавлено/исправлено), но различаться по подаче.

## Version

Версия в имени файла — без `v` префикса: `.ai/release-notes/0.26.0.md`. Это консистентно с заголовком CHANGELOG `## [0.26.0] — ...`. В содержании файла — заголовок с `v` (`# v0.26.0 — 2026-06-13`).

## Required Fields

Файл должен содержать:

- заголовок `# v{version} — {date}` на первой строке (бот отбрасывает его перед отправкой);
- 1–3 предложения summary на русском — что нового в релизе;
- одну или несколько секций с emoji-заголовками: `🆕 Что нового`, `🔧 Что исправлено`, `⚠️ Заметки`, `📌 Ограничения`;
- пункты внутри секций с буллетом `•`.

## Style

- Писать с точки зрения пользы для пользователя, а не реализации.
- Не перечислять модули, пути, идентификаторы требований (FR-*, Р-*), имена фреймворков.
- Не упоминать `**Компоненты:**`, `**Tests:**`, количество прошедших тестов.
- Каждый пункт — одна-две строки с пояснением после тире.
- Удалять пустые секции. Не оставлять заголовок без содержания.
- Конкретные действия пользователя в `⚠️ Заметки`: «обновите привязки», «проверьте даты», «перейдите в раздел X».

## Sources of Content

1. **Spec** — мотивация и польза фичи для пользователя, пользовательские сценарии.
2. **CHANGELOG entry** — точные правки для проверки фактов.
3. **`git log {main}..HEAD --oneline`** — детали, не попавшие в spec/CHANGELOG.

Если spec не описывает пользовательскую пользу (только технические требования) — выводить пользу из характера изменений: «теперь работает X», «видите Y», «не нужно делать Z вручную».

## Process

1. Прочитать `assets/release-notes-template.md` — выбрать spec или small_fix шаблон.
2. Заполнить секции на русском из источников контента.
3. Удалить секции без содержания.
4. Проверить, что нет технических деталей (paths, modules, tests count).
5. Прочитать итог вслух — текст должен быть понятен нетехническую пользователю.
