# UI Verification

Протокол решения о UI-проверке, подготовки сценария и сбора доказательств видимого поведения на шаге тестирования. Браузерные шаги исполняет **основной агент** сессии: browser-инструменты принадлежат его контексту и недоступны субагентам. Инструменты и приёмы — по навыку `playwright-testing`.

## Решение о необходимости UI-проверки

UI-проверка нужна, если выполняется хотя бы одно:

- дифф релиза затрагивает шаблоны, страницы, статику (js/css) или web-маршруты с HTML-ответами целевого проекта;
- в спецификации релиза есть пользовательские сценарии или критерии, сформулированные через видимое поведение («пользователь видит», «кнопка открывает»);
- участник проверки сообщил о видимом поведении, не покрытом кодовыми слоями тестов.

Не нужна (решение «нет» фиксируется с причиной):

- изменения только внутренних модулей, миграций, CLI;
- docs-only релиз — UI-агент и браузерный прогон не требуются, применимость объясняется словами.

Положительное решение фиксируется как UI-needed с причиной: какая видимая функциональность и из какого критерия.

## Сценарист

Сценарий готовит роль `workflow-ui-scenarist` (шаблон — `templates/agents/workflow-ui-scenarist.md`). Пакет задачи обязан содержать:

- **repo_root**, **branch**, **spec_path**;
- **ui_scope** — пользовательские функции и их критерии видимого поведения;
- **changed_ui_files** — затронутые шаблоны, страницы, статика, web-маршруты;
- **scenario_output_path** — абсолютный путь файла сценария в каталоге запуска;
- **environment_hints** — как поднимается стенд (команда из исходников проекта), base URL, тестовые данные: только выделенные фикстуры/тестовые аккаунты, без реальных пользовательских аккаунтов; подсказки для доказательства identity стенда.

Сценарист проверяет каждый URL/маршрут и видимый label по исходникам проекта: шаг, указывающий на несуществующий маршрут, обесценивает сценарий. Отчёт сценариста: `Verdict: scenario_ready | blocked`; отсутствует обязательное поле пакета — ответ `INSUFFICIENT_CONTEXT: missing {field_name}`. Возвраты сценаристу — лимитированы (по умолчанию два).

Сценарий совместим с протоколом ниже: шаги именуют browser-инструменты из фактически доступного набора, предусловия включают identity стенда и изоляцию данных, секция Evidence перечисляет имена файлов доказательств.

## Identity окружения и изоляция (перед исполнением)

Перед любым UI-шагом или замером основной агент доказывает, что процесс/стенд принадлежит проверяемым repo/worktree и ревизии:

1. Зафиксировать ожидание: worktree проверки, его ревизия (`git rev-parse HEAD`), base URL.
2. Доказать принадлежность: процесс запущен этим запуском (PID записан), или командная строка/рабочий каталог процесса указывает на этот worktree, или стенд отдаёт маркер ревизии, совпадающий с ревизией worktree.
3. HTTP 200 или занятый порт — не proof identity: ответить может соседний клон на том же порту; чужой endpoint не принимается как свой.
4. Тестовые данные изолированы: только фикстуры/тестовые аккаунты из предусловий сценария; реальные аккаунты и общие базы запрещены.
5. Fixture-предусловия проверены до начала; непригодное окружение → **blocked** с причиной, не имитация проверки.

## Исполнение (основной агент)

1. Поднять окружение по предусловиям сценария (команда подъёма — из исходников проекта, не выдуманная).
2. Пройти шаги таблицы сценария доступными browser-инструментами по навыку `playwright-testing`: каждый шаг — действие → ожидание → наблюдение → assertion; цели шагов разрешаются в `ref` через свежий `browser_snapshot`; минимальная область snapshot.
3. Собрать доказательства файлами в каталог запуска под именами из секции Evidence: скриншоты по шагам, console-лог, network-лог, responsive-доказательства по брейкпоинтам проекта (viewport-инструментом, если доступен).
4. Выполнить cleanup сценария: только процессы/данные этого запуска с подтверждённым ownership и перепроверенной целью; чужие процессы и dev/prod базы не останавливаются и не очищаются.

## Результаты

- Все шаги сошлись → отчёт «UI OK»: число шагов и пути файлов-доказательств.
- Шаг дал неожиданный результат → **дефект с доказательством**, не остановка и не замалчивание: зафиксировать шаг/ожидание/факт + файл-доказательство, восстановить состояние (reload/re-login) и продолжить сценарий до конца — один прогон собирает все дефекты. Исполнитель не чинит код молча.
- Сценарий неисполним (окружение не поднимается, identity не доказана, browser-capability недоступна или её параметров недостаточно) → **blocked** с причиной; фиктивный UI PASS запрещён. Применимость и неприменимость объясняются явно.
