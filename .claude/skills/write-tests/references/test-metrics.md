# Test Metrics

Протокол измерения метрик прогона тестов, сравнения с мягкими порогами и записи
истории в `.ai/TESTS_ARCHITECTURE.md` целевого проекта (файл устанавливается из
`templates/TESTS_ARCHITECTURE.md.tpl`). Применяется в финальной фазе навыка
`write-tests` после GREEN-прогона.

## Источник порогов — только YAML

Все цели и лимиты читаются из `.ai/workflow.yaml` общим resolver и только
оттуда:

| Назначение | Путь в YAML |
|---|---|
| Целевое время быстрого набора | `defaults.budgets.testing.fast_suite_target_seconds` |
| Целевое время медленного набора | `defaults.budgets.testing.slow_tier_target_seconds` |
| Целевое время самого медленного теста | `defaults.budgets.testing.slowest_test_target_seconds` |
| Бюджет одной команды | `defaults.budgets.checks.command_seconds` |
| Предел зависания | `defaults.budgets.checks.hang_seconds` |

В файлах навыка и в отчётах порог называется путём YAML, а не числом. Значения
YAML навык никогда не меняет сам (см. «Повторные превышения»). Достаточность
набора доказывается manifest и именованными sets; реестры поведения и
процентные пороги покрытия не применяются.

## Метрики

| Метрика | Что измеряет | Как снимается |
|---|---|---|
| `suite_runtime` | время быстрого набора (основной set, без медленного набора) | сумма `duration_seconds` записей основного set в manifest, либо строка `passed in N.NNs` одного budget-wrapped прогона |
| `slow_tier_runtime` | время медленного набора (именованный tier-set) | отдельный budget-wrapped прогон этого set; пропуск допустим только с обоснованием (релиз не затронул модули набора), обоснование попадает в отчёт и в строку истории |
| `slowest_tests` | самые медленные тесты прогона | `--durations` того же прогона; каждый указанный тест сравнивается с `defaults.budgets.testing.slowest_test_target_seconds` |
| `layer_counts` | число тестов по слоям/каталогам | collected node IDs из плана (`scripts/test_evidence.py plan`) либо отдельный `--collect-only -q` прогон |
| `curator_delta` | тесты, удалённые/продвинутые куратором в этом запуске | отчёт куратора этого запуска |
| `layer_diversity` | сколько слоёв задействовано новыми тестами запуска | отчёт автора тестов этого запуска |

Все числа берутся из реальных прогонов этого запуска, не из памяти прошлых
релизов.

## Протокол измерения

1. Каждая команда измерения оборачивается бюджетом одной команды
   (`defaults.budgets.checks.command_seconds`), вывод пишется в файл, без
   pipe. Процесс, переживший предел зависания
   (`defaults.budgets.checks.hang_seconds`), — зависание: убить дерево
   процессов, лог сохранить, прогон считать незавершённым.
2. Один прогон снимает `suite_runtime` и `slowest_tests`; медленный набор —
   отдельным прогоном и только если его модули затронуты релизом.
3. `layer_counts` — collect-прогоном или из уже собранного плана.
4. Выбор scope, чанки и сверка executed/expected выполняет движок
   `scripts/test_evidence.py` (подкоманды `plan` и `reconcile`), формат
   подтверждается схемой `schemas/test-evidence.json`; здесь это не
   переописывается. Manifest — единственный источник чисел строки истории.

## Мягкие пороги и повторные превышения

Превышение или недостижение мягкого порога (метрика, путь YAML, фактическое
значение, вероятная причина):

- фиксируется предупреждением в финальном отчёте навыка;
- переносится в колонку «Предупреждения» строки истории;
- не блокирует завершение шага и коммит;
- при **втором подряд** превышении того же порога (предыдущий запуск с
  превышением виден в строке истории либо в диагностическом отчёте
  незавершённого прогона) финальный отчёт обязан содержать предложение
  пользователю: задача на оптимизацию или пересмотр значения в
  `.ai/workflow.yaml`. Молчаливое накопление повторных превышений не
  допускается;
- изменение значений YAML — только решение пользователя или согласованный
  пункт работы; навык не повышает и не понижает пороги самостоятельно.

## Запись истории

Строка истории в `.ai/TESTS_ARCHITECTURE.md` пишется **только для завершённого
прогона**: manifest со `run_status: completed`. Незавершённый прогон (реестр
дефектов, таймаут без summary, зависание, mismatch) остаётся диагностическим
отчётом в каталоге запуска вместе со своим manifest (`run_status: incomplete`);
его числа можно цитировать в отчёте, но строка истории не пишется, дефекты
сохраняются.

Строка собирается из полей manifest (имена — по `schemas/test-evidence.json`):
`branch`, `tested_commit`, `reconciliation.completed_sets` и
`reconciliation.total_sets`, сумма `records[].summary`, сумма
`records[].duration_seconds`, предупреждения по порогам YAML. Схема колонок
строки — `templates/TESTS_ARCHITECTURE.md.tpl`.

Одновременно обновляются секции слоёв и фикстур, если появились новые каталоги,
фикстуры, маркеры: файл архитектуры тестов описывает suite таким, каким он стал
после релиза. Источник — Architecture Notes отчётов куратора и автора тестов;
структурные факты применяются сразу, изменения конвенций и порогов — только
предложением пользователю в финальном отчёте.
