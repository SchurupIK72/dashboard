# Scope Classification

Ключевой вопрос: это локальный fix или нужна `plan-release`?

## Small-Fix подходит

| Признак | Да |
|---|---|
| Файлы | до warning-порога (по умолчанию 3, из `.ai/workflow.yaml` → `policies.small_fix.file_warning_threshold`); превышение — объяснение целостности задачи, не отказ |
| Поведение | точечная регрессия или ошибка |
| Архитектура | решение очевидно из существующего паттерна |
| Контракты | публичный API/schema/protocol не меняются |
| Проверка | можно проверить одной targeted проверкой или существующим test suite |
| Риск | низкий или средний, локальный |

## Направить в plan-release

Эскалация идёт по содержанию задачи, независимо от числа файлов:

| Признак | Причина |
|---|---|
| Новый публичный contract | требует явных acceptance criteria |
| Миграция/schema change | нужен план и rollback — даже в 1 файле |
| Изменение протокола интеграции | высок риск совместимости |
| Новые возможности вместо исправления | это уже не fix |
| Несколько этапов | apply-small-fix не имеет stage tracking |
| Продуктовая неоднозначность | решение должен принять пользователь до ТЗ |
| Перестройка архитектуры | требует проектирования |

## Warning-порог по файлам

Порог `policies.small_fix.file_warning_threshold` (эффективное значение 3) — warning, не запрет:

- больше порога → маршрут остаётся `apply-small-fix`, но в отчёте обязательно объяснение целостности задачи (почему это один локальный обратимый фикс);
- объяснение отсутствует → STOP и вопрос о целостности, а не автоматический переход в `plan-release`.

## Механическое исключение

Однотипное безопасное изменение (rename импорта, форматирование одной строки, обновление одинакового ключа) сверх порога допустимо без развёрнутого объяснения — коротко указать механический характер в отчёте.
