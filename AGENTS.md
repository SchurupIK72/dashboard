# Dashboard

Веб-дашборд для совместного путешествия по Вьетнаму (2 компании, 3 пользователя): список покупок, дела, учёт расходов со справедливым делением по чекам и вычетом личных трат (корм собаки), погода, курсы RUB/USD к VND и BTC/ETH с графиками. Python/FastAPI + SQLite + Jinja2/HTMX, запуск на VPS или локально в Docker.

Этот файл — инструкции для хоста Codex. Конфигурация Claude — `CLAUDE.md` и `.claude/`.

## Политика хостов: делегирование и приёмка

Для каждого хоста действует своя секция ниже; при конфликте с несовместимыми
инструкциями навыков побеждает секция хоста. Вложенное делегирование запрещено
на всех хостах: субагент никогда не порождает субагентов.

Этапная advisory-роль репортёра импакта едина для всех хостов: после закрытия
этапа `implement-spec-stage` основной агент запускает ровно одного
субагента-репортёра изменений (логическая роль `impact_reporter`, модель и
бюджет — из общих настроек YAML). Отчёт — смысл пунктов ТЗ, воздействие на
возможности/процессы/качества, минимум одна mermaid-диаграмма и одна сводная
таблица — предъявляется пользователю в чате целиком; сбой репортёра не
переоткрывает закрытый этап и не влияет на приёмку.

### Codex

- Все субагенты Codex используют `gpt-6.1-sol`, `model_reasoning_effort = "low"`,
  независимо от роли и сложности. Настройки модели основного агента не меняются.
  При недоступности модели или изоляции — остановка с сообщением пользователю;
  автоматическая замена запрещена.
- Профиль исполнителя (product source): `templates/codex/workflow_implementer.toml`;
  runtime-копия — `.codex/agents/workflow_implementer.toml`. Если API запуска не
  поддерживает выбор именованного профиля, явно передавать `gpt-6.1-sol`,
  reasoning effort `low` и инструкции роли вместе с task package; не наследовать
  настройки основного агента.
- Этапная роль репортёра импакта (после закрытия этапа `implement-spec-stage`):
  product source — `templates/codex/workflow_impact_reporter.toml`, runtime-копия —
  `.codex/agents/workflow_impact_reporter.toml`. Ровно один репортёр на закрытый
  этап, advisory: не пишет код, тесты и статусы, не участвует в приёмке; модель и
  бюджет — из общих настроек (`.ai/workflow.yaml`).
- На каждый пункт текущего шага создавать ровно одного субагента
  `workflow_implementer`. Он полностью отвечает за свой пункт: самостоятельно
  исследует код и требования, выбирает решение, реализует изменения, выполняет
  локальные проверки и исправляет замечания. Отдельных исследователя,
  тестировщика или ревьюера для пункта реализации не запускать.
- Передавать изолированный task package (без истории чата): корень проекта,
  ветку и base commit, item_baseline, спецификацию, шаг и ID пункта,
  формулировку пункта, требования и критерии, границы, разрешённые файлы,
  зависимости, принятые материалы, решения пользователя, команды и бюджет
  проверок, пути отчётов; пустые списки обозначать явно `[]`. Предварительный
  отчёт исследователя не требуется: исследование входит в работу исполнителя.
- Приёмку ведёт основной агент лично: пишет acceptance-тесты, запускает их,
  проверяет diff, границы изменений и соответствие требованиям, сохраняет отчёт
  и решает, принят ли пункт. Субагента-приёмщика не создавать. Исполнитель не
  пишет acceptance-тесты и не принимает собственную работу.
- Приёмка доказывает каждый обязательный критерий: матрица с независимым
  ожидаемым результатом, источником, доказательством и статусом
  PASS/FAIL/BLOCKED/N/A; формальный аудит по гейтам F1–F6 (границы, требования,
  совместимость контрактов, применимые границы и ошибки, правила проекта,
  достоверность проверок) — у каждого гейта доказательство и статус, баллы не
  компенсируют FAIL/BLOCKED. Проверяется достаточность доказательств: путь
  вход → результат → потребитель и контрпример «проверка зелёная, обещание
  нарушено» либо обоснование его отсутствия. Вердикт: passed только при полном
  доказательстве применимых критериев и гейтов; доказанное нарушение — failed,
  отсутствие обязательного доказательства — blocked, вкусовые замечания —
  advisory и не блокируют. Отчёт приёмки — ровно девять разделов, цель 3000
  токенов без символьного потолка.
- Замечания возвращать тому же субагенту, без создания нового на каждую
  доработку; счётчик возвратов и бюджет проверок сохраняются. Одна первичная
  проверка плюс максимум два возврата исполнителю по умолчанию; замечания
  формальной проверки основного агента входят в тот же бюджет; третья
  неуспешная проверка — остановка и вопрос пользователю; пересоздание
  субагента, возобновление запуска и любое настроенное переопределение
  счётчик не сбрасывают. После появления слоя настроек число возвратов
  берётся из политики приёмки, не из пресетов. Команда проверок — не дольше
  150 с (выживший процесс дольше 200 с — hang), ограничение дерева
  процессов, лог без pipe; лимиты по умолчанию действуют и без файла
  тест-конфигурации. Статусы спецификации и коммиты ведёт основной агент;
  `[x]` — только после успешной приёмки.
- Остальные профили используются только для самостоятельных задач
  соответствующего шага workflow, а не как дополнительные роли одного пункта
  реализации. Независимые пункты можно выполнять параллельно при
  непересекающихся файлах; зависимые — после приёмки зависимостей.

### Claude

- Действует цепочка researcher → implementer → tester: исследователь собирает
  факты, исполнитель реализует пункт по принятому отчёту, приёмщик независимо
  пишет acceptance-тесты и проверяет их. Определения ролей (product source) —
  `templates/agents/{role}.md`: workflow-researcher, workflow-implementer,
  workflow-acceptance-tester, workflow-spec-reviewer, workflow-impact-reporter
  и остальные роли workflow.
- Уровни модели выбираются по таблице сложности вызывающего навыка; алиасы
  (`haiku`, `sonnet`, `opus`) разрешаются настройками пользователя, модель
  основной сессии не меняется автоматически. Пакет исполнителя на claude может
  дополнительно содержать принятый отчёт исследователя (`research_report`).
- Приёмка — вердикт приёмщика плюс формальная проверка основным агентом;
  замечания возвращаются тому же исполнителю.

## Workflow

**Один шаг за сессию.** За сессию выполняется только один навык workflow.
Основной маршрут использует ТЗ. Параллельный маршрут `small-fix` предназначен только для небольших фиксов без ТЗ и требует короткую постановку задачи из диалога (симптом/ожидаемое поведение/границы/проверка готовности); режим диалога (Default или Plan) не гейт.

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────┐
│  plan-release   │────►│implement-spec-stage│────►│ write-tests │────┐
│  ① ТЗ + Ветка   │     │ ② Реализация      │     │ ③ Тесты    │    │
└─────────────────┘     └──────────────────┘     └─────────────┘    │
                                                                     ▼
┌─────────────────┐                                            ┌──────────────────┐
│  apply-small-fix│───────────────────────────────────────────►│ integrate-release │
│ F① Fix          │                                            │ ④ Мерж            │
└─────────────────┘                                            └──────────────────┘
```

### Основной маршрут

| Шаг | Навык | ENTRY | EXIT |
| --- | --- | --- | --- |
| ① | `plan-release` | branch: `main` | `.ai/specs/{type}-v{version}-{slug}.md` создан, ветка `{type}/v{version}-{slug}` |
| ② | `implement-spec-stage` | spec существует, есть ⬜ этапы | все этапы ✅ |
| ③ | `write-tests` | все этапы ✅ | тесты GREEN |
| ④ | `integrate-release` | тесты GREEN | branch: `main`, spec в `archive/`, version artifacts синхронизированы |

### Небольшой фикс

| Шаг | Навык | ENTRY | EXIT |
| --- | --- | --- | --- |
| F① | `apply-small-fix` | branch: `main`, локальный фикс без ТЗ + короткая постановка (symptom/expected/scope/verification) | `fix/{slug}` + commit + проверка |
| ④ | `integrate-release` | `fix/*`, нет spec, нет uncommitted changes | branch: `main`, CHANGELOG обновлён |

### Правила переходов

1. **Нельзя пропускать шаги внутри выбранного маршрута** — каждый навык проверяет ENTRY условия
2. **Один шаг за сессию** — после завершения `/clear`
3. **Явный next_skill** — каждый навык указывает следующий шаг
4. **`apply-small-fix` требует короткую постановку** — symptom/expected/scope/verification собираются из диалога в любом режиме (Default или Plan); режим UI не гейт
5. **Если навык ошибся** — зафиксировать ошибку, исправить, спросить пользователя
6. **Каждое ТЗ = новый релиз** — `plan-release` выбирает будущую SemVer-версию `MAJOR.MINOR.PATCH` и использует её в заголовке ТЗ, spec-файле и ветке: `{type}-v{version}-{slug}.md` и `{type}/v{version}-{slug}`
7. **Версия синхронизируется на merge** — `integrate-release` обновляет `.ai/CHANGELOG.md` и все найденные version artifacts проекта (`pyproject.toml`, `package.json`, `VERSION`, `__version__` и аналоги) до версии релиза

### Workflow State Validation

`scripts/validate_workflow_state.py --step {skill}` — ENTRY-проверка declared workflow state. Проверяет маршрут, spec, статусы этапов и version consistency. Не заменяет фактические проверки навыков.

├── tests/                ← pytest (unit/, integration/)
